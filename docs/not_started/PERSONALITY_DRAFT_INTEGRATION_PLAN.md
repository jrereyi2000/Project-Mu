# Project Mu: Personality Draft and Person Lifecycle Integration Plan

**Status:** approved by JR (2026-11-03), Q1–Q4 settled as recommended (§8); not built. Approval covers building the units; applying the inventory to a real franchise, migrations and activation each still need JR's separate go-ahead (§6 gates).
**Scope (JR, 2026-11-03, PERSONALITY_PLAN §5.1, D11–D13):** every player gets one persistent profile. Existing players in the starting 2026 save get engine-generated profiles once, at the league start, with no research into the real player; draft prospects get theirs at draft-class entry, including real-player imported classes. Players named after real people are fictional characters inspired by them, so they are classified `generated` like any other player. JR can edit any profile. Existing real coaches get reviewed profiles from a separate workstream (not planned yet); this plan registers their identities and aliases and initializes coaches only from that workstream's reviewed manifest.
**Builds on:** PROJECT_SPEC §2.10, §2.18, §2.19, §3.3c, §3.3g, §3.3p, §6.0b, §7.11; [Personality Plan](../in_progress/PERSONALITY_PLAN.md) §5.1–5.2; [Generated Effects Design](../in_progress/PERSONALITY_GENERATED_EFFECTS_DESIGN.md) §4–5; `personality/README.md`.

**Goal:** Initialize every player in the starting 2026 save and every prospect once, before personality-dependent decisions, and preserve identity into player/staff records through the 2026–2033 CPU simulation and JR's 2034 takeover. A person whose identity can't be established stays pending; nothing becomes generated by guesswork about who someone is.

**Delivers:** proposed `personality/lifecycle.py`, `personality/lifecycle_store.py`, `tools/personality_inventory.py`, lifecycle sidecars, ingestion/scouting/staff hooks, reviewed manifests and synthetic verification. All new names below are proposals, not claims that functions already exist.

The [cap-relative plan](../done/CAP_RELATIVE_CONTRACTS_PLAN.md) (built and on main 2026-11-02) owns pricing, the career-earnings ledger and the slider band; none of it is duplicated here. ## 1. Scope

**In:** starting-checkpoint inventory of Draft/Signed/PracticeSquad/FreeAgent people (every existing player gets a generated profile, plus all prospects beyond pick 224); identity registration for existing coaches and other decision-makers; participating staff/decision-makers supplied through explicit exports; authoritative classification; durable aliases; one-time initialization; verified draft/UDFA handoffs; offline previews, reviewed application, replay/cutoff/version protections, quarantine and rollback; hooks before future personality decisions.

**Out:** formulas/calibration for contracts, progression, relationships, requests, retirement or coaching careers; salary/earnings work; event-to-trait policies; save writes; researching real players (none is researched) or real coaches (the coach-profile workstream does that); Focus/PT inference; public hidden-profile UI; replacing core or scouting's noisy observation model; automatic legacy adoption or origin changes.

Money preference is independent of work ethic; quiet is not low confidence; hometown is not attachment. Ring Chaser remains a latent generated trait, not proof of financial security or a usable contender role. Earned attachment must come from tenure, meaningful relationships, role and treatment, never relationship count. Owning features enforce those rules.

## 2. Design

### 2.1 Identity and classification

Recommended universe ID: `mu:<registered UUID>`, bound once to verified Madden league ID, starting snapshot SHA256 and 2026 cutoff. Independent of registry label, DB name or filename. Resume/restore preserves it; independent simulation forks get a new one by explicit declaration. Reject DB league-stamp mismatch before mutation. A filename-fallback registry entry cannot activate lifecycle binding.

**Adopting the scouting plan's prospect ID (2026-11-03).** The approved V2.10 scouting plan (`SCOUTING_REVAMP_PLAN.md` §2.1b) builds first and allocates `prospect_uid = uuid5(MU_PROSPECT_NS, birth_key)` in `scout_prospect_ids`, with `birth_key` `save-pgid:<class>:<pgid>` (save classes) or `board:<class>:<first prospect_key>` (scanned classes). This plan adopts it: use `prospect_uid` as `source_person_id` for those prospects. If it must allocate a different UUID, it writes it to `scout_prospect_ids.source_person_id` and binds the alias `scout-uid`/`prospect_uid` to it, so existing scouting rows and inbox threads still resolve.

Allocate an immutable `source_person_id` UUID at verified first entry. Native sources may derive it deterministically from universe/source-domain/first-seen class-or-checkpoint/pgid only after continuity is verified. Store birth key `source:<source_person_id>` permanently; do not recompute after status/name/class/pgid changes. pgid is a lifetime-scoped alias. If reused, create a new lifetime namespace and require reviewed mapping. Imported CSV/class sources require supplier immutable IDs or a durable UUID sidecar created once and retained through row reordering/renames. No name/rank/row-index hashes as birth keys. Missing mapping means pending.

Prospect through retirement uses core role `player`. HC/OC/DC use `coach`, binding distinct `db-coach`/`db-coordinator` namespaces to the same identity. Existing core supports `gm`, `owner`, `scout`. A human crossing core roles (a player who becomes a coach) gets a new profile linked to the old one through the core extensions plan's `store.link_role_change` (sliders and role-eligible traits carried over, nothing redrawn). Until that is built, mark `cross_role_review`; never silently clone a profile.

Classification receipt fields: `origin` (`generated|real|unknown`), `source_ref`, `source_sha256`, `reviewer`, `reason`, `reviewed_at`, `effective_at`, `scope`. Players: JR's rollout decision is the classification. One reviewed receipt classifies the whole verified 2026 starting roster `generated`, and each class (native or imported real-player) is classified `generated` at entry by its class receipt, after provenance, completeness and exception checks. What has to be verified is identity and continuity, not whether the person is real. Coaches: existing real coaches are `real`, initialized only from the coach-profile workstream's reviewed manifest; fictional coaches created by the carousel are `generated` (§2.5). Conflicts quarantine. Evidence stays core-owned provenance; features read reviewed profiles in full (core extensions plan D1).

Unknown means an unresolved identity or mapping, not a real person. Default: inventory pending, no `ensure('unknown')`. Existing unknown profiles remain neutral pending core adoption. This avoids locking an unreviewed person into an origin that ensure cannot change. Missing and unknown remain distinct statuses.

### 2.2 Integration sidecars

Migration `db/migrations/2027_01_24_personality_lifecycle.sql` (reserved in PERSONALITY_PLAN §5.3; recheck at build) depends on legacy/core migrations. DDL seeds nothing.

| Table | Exact proposed data contract |
|---|---|
| `persona_lifecycle_universes` | `universe_id TEXT PRIMARY KEY`, `league_id TEXT NOT NULL UNIQUE`, `initial_snapshot_sha256 TEXT NOT NULL`, `start_season INT NOT NULL`, `start_cutoff JSONB NOT NULL`, `manifest_version TEXT NOT NULL`. Immutable registration; explicit correction review. |
| `persona_lifecycle_people` | `universe_id TEXT`, `source_person_id UUID`, `role TEXT`, `birth_key TEXT`, `classification TEXT` checked three origins, `classification_receipt JSONB NOT NULL`, `first_seen JSONB NOT NULL`, `state TEXT` checked pending/ready/quarantined/archived, `persona_id VARCHAR(64) NULL`, `revision INT NOT NULL DEFAULT 0`; PK `(universe_id,source_person_id,role)`, unique `(universe_id,role,birth_key)`, nullable composite FK `(role,persona_id)` to core. |
| `persona_lifecycle_bindings` | `universe_id TEXT`, `role TEXT`, `namespace TEXT`, `external_id TEXT`, `source_person_id UUID`, `valid_from JSONB NOT NULL`, `valid_to JSONB NULL`, `receipt JSONB NOT NULL`; PK `(universe_id,role,namespace,external_id)`, composite FK to lifecycle person. Conflicts never overwrite. |
| `persona_lifecycle_batches` | `batch_id TEXT PRIMARY KEY` (canonical manifest hash), `universe_id TEXT NOT NULL` FK, `manifest JSONB NOT NULL`, `before_state JSONB NOT NULL`, `after_state JSONB NOT NULL`, `status TEXT` checked applied/reverted, `applied_at TIMESTAMPTZ NOT NULL`, `review_receipt JSONB NOT NULL`. Replay compares complete canonical payload. |

All person/binding key columns are NOT NULL; universe FKs apply to each table. Bindings retain pending/time-scoped observations. Only verified identity aliases are also written with `store.bind_alias`: `source-person`/UUID, `save-pgid:<lifetime>`/decimal pgid, `db-player`/DB ID. Replaceable board alias: `draft:<class>:<capture-sha>`/board ID. `scout:<class>`/prospect_key is allowed only when unique/verified. Rename may add another alias. No FK from durable identity to replaceable board rows, no cascade deletion on reload. Reject ID reuse following unrelated DB reseeding; checkpoint restore must preserve identity ledgers.

### 2.3 Proposed Python interfaces

New pure contracts in `personality/lifecycle.py`; cursor persistence in `personality/lifecycle_store.py`:

```python
validate_inventory(snapshot: dict, classifications: dict, *, universe: dict,
                   cutoff: dict, staff: list[dict]) -> dict
plan_lifecycle(inventory: dict, existing: dict, *, core_version: str,
               catalogue_version: str) -> dict
validate_handoff(candidate: dict, bindings: list[dict]) -> dict
apply_lifecycle(cur, manifest: dict, *, expected_hash: str,
                review_receipt: dict) -> dict
resolve_person(cur, universe_id: str, role: str, namespace: str,
               external_id: str, *, cutoff: dict, feature: str) -> dict
require_ready(cur, references: list[dict], *, cutoff: dict,
              feature: str, mode: str) -> dict
```

Manifest schema `personality-lifecycle-v1`: `universe`, `cutoff`, `input_hashes`, `reader_version`, `core_version`, `catalogue_version`, `preconditions`, sorted `people`, `actions`, `issues`, `counts`, `manifest_sha256`. Person: source ID, role, attestation, first-seen cutoff, aliases/receipts, expected profile revision/hash, proposed profile hash; action initialize/bind/retain/pending/quarantine/archive. Include restricted profile preview for review, never public scouting data. JR's edits before first use (PERSONALITY_PLAN D4) go here: he changes a proposed profile in the manifest, the hash changes, and his review receipt records it. Edits after first use go through the core's JR override (D4), planned in the [core extensions plan](../done/PERSONALITY_CORE_EXTENSIONS_PLAN.md). Canonical hash uses sorted keys/stable arrays and excludes volatile export timestamp. No DSNs/credentials.

Cutoff: `{season:int, phase:str, sequence:int}` with phase ordering fixed by spike, not lexical order or wall-clock import time. Sequence distinguishes same-phase captures. Review receipt: `{reviewer,reviewed_manifest_sha256,decision,reason,reviewed_at}`.

Resolver returns `{status,identity,view,profile_revision,profile_hash,reason,cutoff}`; status ready/missing/unknown/ambiguous/future/quarantined. Ready reads core then feature_view. Valid missing/unknown is neutral; invalid profiles/schema/storage raise, never randomize. `require_ready(mode='observe')` reports without changing current decisions; enforce blocks unresolved required references for personality-dependent decisions. Enforce does not itself activate any effect. Feature owner explicitly decides whether neutral fallback is allowed for a missing participant.

Core has no historical lookup today. Support current state at the accepted cutoff and exact replay through pinned exported/decision snapshots. Earlier-cutoff recomputation after evolution returns explicit unsupported historical-resolution error, never today's profile. Historical recomputation uses the core extensions plan's `store.read_as_of`; until it is built, it stays blocked. Check effective bindings/first-seen cutoff first.

### 2.4 Entry and handoff order

1. Verify universe/checkpoint; preview complete inventory and classification; review manifest. Parsing a snapshot never implicitly creates profiles.
2. In accepted loader transaction, preserve source pgid mapping before Prospect conversion, load ordinary rows, reconcile existing/new board mapping, apply reviewed lifecycle actions, verify aliases, commit together. Existing-board early return still reconciles/report pending. Partial boards cannot map by rank.
3. Recurring class initialization requires approved class-source provenance policy and explicit receipt. Call ensure once per verified generated entrant, bind aliases and receipt before personality-dependent scouting. Removed/withdrawn entries archive observations, not identity. Catalogue upgrades, trades, re-entry, rank/name changes never redraw. Four traits and seeded budget 30 remain core defaults.
4. Add observe-mode checks to scouting init/run/catch_up. Existing truth/noise/grades/interview text remain identical. Later interview features observe pre-existing truth; current strong/mixed prose neither creates nor changes personality. Legacy key collisions block affected activation, not quietly merge people.
5. Draft -> Signed/PracticeSquad/FreeAgent verifies same pgid lifetime or applied import mapping, resolves original identity, then binds player DB ID. Pick/team are context, not identity. UDFA needs neither actual_pick nor roster team. Roster-first unresolved rows remain pending; never seed a second profile.
6. CSV/OCR `load_capture.load_prospects` accepts reviewed source-ID sidecar. Board replacement/rookie linking retains existing non-personality behavior; name match is candidate only. Reviewed handoff maps source UUID -> player DB ID/pgid with capture hashes. Off-board recap inserts remain pending until classified. No automatic recap-source origin inference.
7. Teleport/import mapping needs reviewed candidate plus post-write snapshot verification. Current donor report alone cannot bind personality. Consume receipt without editing save writer/donor algorithm. Failure quarantines mapping.

Proposed optional `personality_context=None` argument on `load_snapshot` and `load_prospects`; loader CLIs gain `--personality-manifest PATH` and `--personality-review PATH`. Without context, ordinary loading remains available in observe mode and reports `personality_pending`. No automatic repair/reseed retry. Accepted action conflicts in enforce mode abort caller transaction. Preview calls no mutation helper.

### 2.5 Initial-save inventory and staff

Inventory actual 2026 starting export, not an assumed 2034/2037 archive. Every player in it, real-inspired or Madden-generated, gets a generated profile; future classes (native or imported real-player) do too. Include full class/free agents and supplied participating HC/OC/DC/GM/owner/scout records. Report counts by origin/status/role/source, unsupported statuses/readers, duplicate/missing pgids, unresolved identities and unmanaged legacy profiles. Nothing waits on research: players aren't researched, and coaches without a reviewed profile yet stay pending.

Fictional coaching creation in hiring_cycle or fire_coordinator gets a durable creation event ID and source UUID, not name/team/job. Bind coordinator ID in the same transaction; HC promotion adds coach alias to same coach identity. Poached/retread people retain identity/classification. A successor inheriting scheme does not inherit predecessor personality. Archive same-cycle temporary identities if their coordinator row is deleted; retain receipt/history. A future personality-dependent candidate policy may create identity before hire, but career/candidate rules remain externally owned.

Existing real coaches use reviewed inventory, supplied as `personality.coach_profiles.lifecycle_entries` from the [real-coach profiles plan](REAL_COACH_PROFILES_PLAN.md): this plan registers their identity and aliases now and applies their profiles when the coach-profile workstream supplies its reviewed manifest; until then they are pending, not neutral-initialized. Future GM/owner/scout creators call apply_lifecycle with durable creator receipts; no new hiring engines or unowned GM policy wiring here. Existing GM personas (phase 3, fictional characters inspired by real GMs) keep their legacy sliders; they are not automatically adopted core profiles. Human cross-role changes remain gated pending core policy.

### 2.6 CLI, replay and recovery

```text
python -m tools.personality_inventory preview --snapshot fixture.json --universe universe.json --classifications classifications.json --cutoff cutoff.json [--staff staff.json] [--existing export.json] --out manifest.json
python -m tools.personality_inventory validate --manifest manifest.json
python -m tools.personality_inventory compare --before manifest.json --after replay.json --out diff.json
```

These commands are fully offline: no DB import/connect, model calls or writes except specified output. Pure core initialization can preview classified candidates. Proposed operational `export --universe ID --out export.json`, `apply --manifest PATH --review PATH --expect-hash HASH`, and `revert --batch ID --expect-after-hash HASH --review PATH` require explicit configured connection, never implicit active franchise. They are implementation proposals, not commands to execute in planning.

Apply checks league stamp, schema fingerprint, input/manifest hashes, expected revisions/bindings, current cutoff and approved versions. Changed input requires new preview/review. Exit 0 valid/applied; 2 invalid input/version; 3 unresolved classification/identity; 4 stale/conflict/schema/profile failure. Preview writes reviewable manifest even with exit 3.

One non-autocommit transaction per bounded class/checkpoint batch. Lock universe and use core per-identity locks; serialize overlapping batches/recheck preconditions. Same accepted batch returns receipt, reused ID/different payload fails. Existing profiles survive catalogue changes; new generation preview must match approved core/catalogue version. No generator substitution.

Missing: observe-neutral reason, explicit reviewed repair if classification/identity proved. Corrupt: quarantine/report, fail active resolution, core-owner audited restore; never redraw. Legacy/unknown: export candidate mappings and compare traits/sliders/history; no direct metadata edits, duplicate-core workaround or automatic adoption. Core-owner adoption/reclassification API is a dependency. Every profile can later evolve from recorded simulation events through core; this plan adds no event-to-trait rules or fabricated prehistory.

Rollback disables enforcement/effects first. Revert only if after-state unchanged, with no subsequent aliases/evolution/decisions. Reverse bindings and exclusively batch-created profile/history rows in FK order; keep reverted batch receipt and shared catalogues. Once downstream use exists, restore consistent checkpoint including decisions/events or make reviewed superseding correction; do not selectively delete personality. DDL rollback only for empty unused integration tables; preserve core/legacy data. Rehearse backup/restore on synthetic scratch. DDL rerun verifies schema fingerprint instead of hiding incompatibility with IF NOT EXISTS.
