# Madden Pilot

The pilot drives Madden 27 on JR's PC so Madden can run experiments while JR is away. It launches the game with a mod pack, checks mods, changes a setting, sims a tuning franchise forward and quits, leaving the save for Project Mu to read. Plan: [`MADDEN_PILOT_AND_TUNING_PLAN.md`](../done/MADDEN_PILOT_AND_TUNING_PLAN.md). Skill: `/madden <task>` (`.claude/skills/madden/SKILL.md`).

## 1. How it works

| Layer | File | Runs in | Does |
|---|---|---|---|
| Driver | `tools/madden_pilot/win_agent.py` | Windows Python (`C:\Madden27Modding\MuPilot\venv`, `MU_WIN_PYTHON`) | `windows`, `focus`, `look --ocr` (captures Madden's client area with mss and reads it with Windows OCR), `key` (hardware scan codes through SendInput), `record` (a frame burst, below), `run`, `kill` (Madden27.exe and MMCModManager.exe only). One JSON line per command. |
| Record | `tools/madden_pilot/win_agent.py record` | Windows Python (`C:\Madden27Modding\MuPilot\venv`, `MU_WIN_PYTHON`) | A burst of client-area JPEGs with mss into `--dir` (`frame_0000.jpg`…): `--seconds` 1–30, `--fps` 1–10 (`MAX_RECORD_FPS`), `--width` downscale. It returns `frames`, `fps_actual` and `size`, and checks the abort gesture on every frame, so a corner hit stops the burst and keeps the frames written so far. Used through `spike-record`; no `/madden` job records yet. |
| Wrapper | `tools/madden_pilot/win.py` | WSL | `call(cmd)` runs the driver and converts paths with `wslpath -w`. |
| Catalog | `tools/madden_pilot/catalog.json` | WSL | Every screen seen so far: its OCR test, its exits, which labels Space may accept, and its safety flags. The `doc` array at the top explains each field. |
| Classifier | `tools/madden_pilot/screens.py` | WSL | `classify(frame)` returns the first screen in catalog order whose words match, else `UNKNOWN`. `border_highlight` reads the **selected row** from the screenshot by containment: the row's own text must lie inside a filled selection band or between an outline's two border runs (a tall portrait card such as `FRANCHISE_LIST`'s tiles is found by pairing its far-apart top and bottom border lines, which must agree on both edges); a truncated label is named only through a screen's `aliases`, and an unreadable selected row reads `None` rather than borrowing a neighbour's border. |
| Navigation | `tools/madden_pilot/navigate.py` | WSL | `Pilot`: `look`, `press`, `wait_for`, `goto` (shortest route over the exits, re-planned after every hop), `confirm_on` (Space only on allowed labels, with the highlight checked), and the stops. |
| Jobs and CLI | `tools/madden_pilot/jobs.py`, `__main__.py`, `checks/` | WSL | The jobs below, `python3 -m tools.madden_pilot <job>`, and the `--dry-run` fake Madden. |

Facts from the spikes (2026-10-30):
- **Not elevated.** Madden runs as the normal user, so SendInput reaches it.
- **The window.** It is called `Madden NFL 27`: a 2560×1440 borderless popup at (0,0).
- **It minimizes whenever it loses focus.** The driver refocuses it before every look and key, and refuses to press a key when it can't. During a run, Claude must be minimized or on another monitor.
- **OCR.** Windows OCR reads labels and headings exactly. It garbles stylised numbers (`OVR` reads as `WR`, `$10.9M` as `SIO.9M`), so screens are classified on labels. Stats always come from the save file, never from OCR.
- **Abort.** Moving the mouse to the top-left screen corner aborts, and so does **holding the right mouse button** (useful when a run keeps taking the focus): the driver checks both before every key and every capture, including inside a focus wait.

## 4. Routes

Arrows are the catalog's exits. `goto(target)` takes the shortest route and plans again after every hop, so an interrupt (Coach Progress) or a recap is handled on the way.

- **Load a tuning franchise:** FRANCHISE_LIST → the `TUNE-<x>` tile → Space → PROGRESSION_WARNING → Proceed → (loading, about 25 s) → HUB_WEEKLY. The list is ordered by **the save's own date** (not the file's mtime — a copy changes only that) and autosaves are tiles of their own. The pilot reads which tile carries the white border, picks the direction from the two labels' x positions when both are on screen, and presses one arrow at a time, looking after each, until the border is on the target; a press that does not move the border is the list's edge, and it then goes the other way. Jumping by the saves folder's order is wrong (2026-11-10). **Every load enters CURRENT FRANCHISES from the main menu.** The pilot backs out to the main menu (at most three Back presses, stopping at `MAIN_MENU`/`MAIN_MENU_RAIL`, or at `FRANCHISE_LANDING` on a one-mode pack) and enters Franchise → CREATE / LOAD again before walking: Madden builds the list when the screen opens, and a list that was already up keeps tiles for saves no longer on disk and misses a clone made while it was up (JR, 2026-11-10; a p2g run walked a stale list and never saw its clone). One more Back on the main menu opens `EXIT_MADDEN`, which is dismissed, never confirmed. **On a one-mode menu pack (Mu Franchise Only) this needs no change:** that pack draws its Franchise panel where the vanilla landing page is, and the rail strip it shares (`LAST PLAYED`, `AUTHENTIC`, …) is what `_leave_to_main_menu` recognises, so the same back-out-and-re-enter lands on the panel and CREATE / LOAD (live 2026-11-11 on Mu Test). Back on it opens `EXIT_MADDEN` too. The walk itself moves **three presses at a time** and looks for the tile anywhere in the frame (a page shows more than three), then steps onto it one tile at a time — one press per look needed minutes for 170 saves. The bordered tile is read against the frame's own names as well as the saves folder's, so a stale list is still readable. **It then checks the load:** the hub's own header must name the same year (and week, in a regular season) as the save file it meant to open, else it stops rather than sim the wrong season (2026-11-10: a lost arrow press loaded the previous save, 2028 week 1, under the name of a 2026 clone).
- **Sim one week:** HUB_WEEKLY → Z → HUB_GAMEDAY → highlight ADVANCE WEEK (border checked) → Space → ADVANCE_MENU → NEXT WEEK → Space → (sim, under 20 s) → COACH_PROGRESS ×3 (Space each) → HUB_WEEKLY (read `2026. WEEK N`).
- **Savepoint:** HUB_WEEKLY → Tab → (back to the hub).
- **Quit a franchise:** hub → Backspace → QUIT_CONFIRM → Up → Space on YES → FRANCHISE_LIST. This writes `<save>-AUTOSAVE`, so it is `TUNE-*` only unless JR allows it.
- **Out of a recap:** WEEKLY_RECAP → Backspace (repeated) → HUB_GAMEDAY.
- **Out of a roster prompt:** ROSTER_DECISION_PROMPT → Backspace → HUB_WEEKLY.
- **Skip a live event** (free agency, and the UDFA event after the draft): the advance is locked, so ADVANCE_LOCKED →
  Space on OK → Z to LIVE_EVENT_FRENZY → hold Escape → LIVE_EVENT_FRENZY_MODAL → Down onto SIMULATE TO END OF FRENZY →
  Space → FREE_AGENCY_ENDED → Space on OK → C to GAMEDAY. The route to ADVANCE_MENU goes through the event, so the
  pilot takes it whenever the week is locked.
- **Draft week:** DRAFT_HUB → Space on START THE NFL DRAFT → DRAFT_LAUNCH → Down → Space on SIMULATE DRAFT. The
  draft sim is long and lands on the recap stop; Mu has already written its picks into the save.
- **Catch-up on the real franchise:** load its tile (allowed for exactly this run) → hub → Z → GAMEDAY → ADVANCE
  WEEK → FORCE ADVANCE → sim → (the save's week must read exactly one later) → Backspace → QUIT_CONFIRM YES
  (`allow_quit`) → main menu → wait for `nfl_mirror_weeks` WRITTEN for the new week → repeat until a LIVE week
  or `--to-week`. The franchise stays closed while the league office replaces the save; the next load re-enters
  CURRENT FRANCHISES from the menu.

Not mapped yet: the way back from a mode landing page to the main menu (the pilot presses Back), settings screens, the post-season, and what Tab shows.

## 5. Jobs

`python3 -m tools.madden_pilot <job> [--run-dir DIR] [--dry-run]`. Each run gets `data/pilot_runs/<YYYY-MM-DD_HHMMSS>_<job>/` with:
- `steps/NNNN_<screen>.png` and `.json`: every look, with its OCR lines;
- `result.json`;
- `stop.json` on a stop.

A Muse session started with `tools/muse_session.sh` **may run these jobs**: the two-step benchmark in [`MUSE_EMBER_ROTATION_PLAN.md`](../done/MUSE_EMBER_ROTATION_PLAN.md) passed on 2026-11-12 (gate and numbers in [`MUSE_EMBER_EVALUATION.md`](MUSE_EMBER_EVALUATION.md) §2–§3), and JR's decision is Muse Spark 1.3 on OpenCode Go. The catalog above is still the driver — a Muse session acts at the stops, it does not replace the routes.

Every job ends with one ntfy summary through `pipeline.notify`, on finish, refusal or stop. A stop also sends its own alert. Exit code 0 means ok or pass, 2 means unknown, 1 means refused or stopped.

| `launch [--pack "Mu Base"]` | Starts Madden with `cmd.exe /c start "" "<MMCModManager.exe>" -launch <pack>`, using `pipeline.game_launch`'s `command` and `manager_exe` helpers (its own `launch()` picks a per-game pack from the database, so it isn't used). It runs the manager **from its own folder** (`launch_cwd`): started from anywhere else, Frosty's executor fails to load the pack ("errors occurred while attempting to load the following mod") and no Madden window ever appears — that working-directory bug cost three launch attempts on 2026-11-12 (MUSE_EMBER_EVALUATION.md §2.2). `--dry-run` replaces the Windows driver with `ScriptedMadden` (in `__main__.py`), a fake Madden built from the catalog:
- each screen shows its `all` words, its first `any` word and its options;
- each exit's last step leads to its target;
- loading a tile, Proceed, NEXT WEEK (three Coach Progress tabs) and Tab are scripted;
- after week 18 the header reads WILD CARD, and the next NEXT WEEK opens an uncatalogued screen;
- `catch-up` uses a fake mirror that reads `nfl_mirror_settings.enabled` true and every week WRITTEN, and turns the week mode LIVE after week 18, so an unqualified dry run stops at the first LIVE week.

It prints the route summary and every look and key. It launches, copies, presses and sends nothing, and it warns if the watcher is running (or, for `catch-up`, that a live run would refuse because it is not).

Not done automatically: killing Madden. `kill` exists in the driver, but no job calls it. A save half written by a killed Madden is worse than a stuck run.

## 6. Safety rules

- **Space** is only pressed through `confirm_on`, only on labels in the screen's `confirm_ok`, and, where the highlight can be read, only with the highlight on that label.
- **Roster cards and decisions** are never selected (`never_select`): Project Mu makes roster decisions through the save writer.
- **Forbidden screens** (delete, and later online, store, sign-in) stop the run on sight. `forbidden_keys` (Q, E) are never pressed.
- **Saves.** Only `CAREER-TUNE-*` saves are loaded, simmed or quit without JR, and never while `pipeline.watch_save` runs. A clone keeps the original's LeagueID, so the watcher would ingest it into the real franchise database. The one exception is `catch-up`: by design it drives the real `CAREER-*` franchise, and only with the watcher running and under `CLAIM · Madden PC`. It refuses a watcher that isn't running, a TUNE clone, and a week that isn't CATCH_UP, and it allows exactly its own save's tile on CURRENT FRANCHISES for that run.
- **Asking first.** Every run asks JR before taking the PC, and says how long it takes. Quitting a non-TUNE franchise asks JR first.
- **Starting a game is `watch-game`'s job**, and it never calls a play: every control between the kickoff and the half's last snap is a supersim one, and the half's last snap is the only football key press (JR, 2026-11-12). Its `--to supersim` route also kicks off, then holds on the super-sim screen so a static mod-check segment is positioned rather than timed. `HUB_GAMEDAY` stays `ADVANCE WEEK` only.
- **Quitting a game** is `watch-game`'s own exit on a `TUNE-*` clone: it pins the pause menu's QUIT GAME, lifts it through the pilot's policy for that run, then confirms only `YES - EXIT TO MENU` in the measured `EXIT GAME` modal. `YES - EXIT TO DESKTOP` and `NO` are refused by the job even if a catalog lists them. No other job can reach QUIT GAME.
- **Never:** online play, purchases, deleting anything.

## 7. Extending the catalog

When a job stops as Unknown:

1. Open `stop.json` and view the screenshot it names (the Read tool shows PNGs). The `steps/NNNN_UNKNOWN.json` next to it holds the OCR lines and words.
2. Add the screen to `tools/madden_pilot/catalog.json`:
   - **Name and words:** an upper-case name; `all`, `any` and `none` taken from OCR **labels** (never numbers). Place it before any screen it shares words with, because the first match wins.
   - **`exits`:** `{TARGET: [[key, n] | ["highlight", LABEL] | ["confirm", LABEL]]}`. Every confirm label must be in `confirm_ok` (the nav tests check this).
   - **`confirm_ok`:** only labels that are safe to accept. A decision gets `[]` with `forbidden_confirm` or `never_select`.
   - **Highlight:** `options`, `default`, `nav` (vertical or horizontal) and `highlight` (`border` or `ocr_order`; both now read the row **inside the selected region** from the image, and a lone bright line is not evidence). `aliases: {LABEL: [other real readings of the same row]}` restores a measured truncated label. `line_is: [PHRASE]` requires a whole OCR line, for a word that also appears inside a ticker.
   - **Flags:**
     - `repeat`: a multi-page screen that looks the same page to page;
     - `wait_or_back`: a video;
     - `forbidden` or `forbidden_keys`;
     - `no_route`: never a target;
     - `todo`: a guess.
   - **`note`:** where it was seen (run dir and step).
3. Add a row to §3 here, and a route to §4 if it adds one.
4. Run `pytest -m "not integration" tests/test_madden_pilot_nav.py tests/test_madden_pilot_jobs.py`, then `--dry-run` the job again.
5. Retry the job, asking JR again for the PC.

- the loading frame between `FRANCHISE_LANDING` CREATE / LOAD and `FRANCHISE_LIST` (reads as UNKNOWN for a second or two);
- what Tab (savepoint) shows;
- the preseason/cutdown stops (PreSeason week 0 and week 3+) and whether the cutdown has its own advance;

## 8. Spikes

For a screen you need explored that the catalog doesn't know, request a spike rather than widening the pilot: one fresh session runs one written brief under a code guard (`tools/madden_pilot/spike.py`) — `spike-start`, `spike-look`, `spike-key`, `spike-confirm`, `spike-goto`, `spike-record`, `spike-check`, `spike-end` and the after-run `spike-analyze` — captures frames and clips, runs fixed asset checks, and posts a report for the requester to catalogue. The guard is above the pilot, not in the agent's judgement: caps, hard-stop words, key and confirm allow-lists, and TUNE-only saves. The brief format, the report format, the guard rules, the vision backends, the asset-check specs and a worked example are in [`MADDEN_SPIKE_AGENT.md`](MADDEN_SPIKE_AGENT.md); the skill is `/madden-spike <brief.json>`. The rules above still hold inside a spike: no roster cards, no online, no purchases, no deletes, and JR's yes before the PC.
